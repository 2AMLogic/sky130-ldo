## Method (reuses the repo harness)

- `mitigation_probe.py` imports `sim/bin/corner-run.py` for xschem netlisting
  (`sim/loop-gain/testbench/tb_loop_gain.sch` -> current `design/ldo_3v3in_1v8out.sch`), `build_deck`,
  PDK resolution and the solver-diagnostic detector. The analyses are `sim/loop-gain/experiment.json`'s
  seven-point deck VERBATIM (same `.nodeset` branch seed, same `op` + `ac` per point, same measurement
  expressions), plus `print`s of the seeded-`op` VOUT and VIN current. Exactly one `ngspice -b`
  per invocation, run sequentially; no grid, no parallelism; ~3 s per run. No `klt sim` batch
  submission was made (nothing here needed a grid; see handoff for the batch gate).
- Seven points per run: C_out 0.33 uF / 10 mOhm at 50, 1, 0 mA; C_out 4.7 uF / 10 mOhm at 50, 1, 0 mA;
  C_out 0.33 uF / 500 mOhm at 50 mA. (Two capacitance endpoints; ESR 10 mOhm plus the one 500 mOhm leg.)
- Edits (applied to the xschem-generated netlist text; raw and edited netlists both saved and hashed):
  `RBLEED VOUT 0 (1.8 V / I)` for the bleed, `C_COMP` value, `XR_CZ` length (W fixed). R_CZ scaling was
  checked against the model (`rcz_resistance/`): L=26/52/104 um -> 150.2k / 300.6k / 601.3k ohm at tt/27C,
  i.e. 0.4998x / 1x / 2.0006x.
- Iq = VIN current (-i(VVIN) of the seeded `op`) minus external load current (VOUT / R_LOAD).
  The bleed resistor is internal, so it stays IN Iq. Cross-check against the `sim/iq` method
  (cold-start settled 200 ms transient, its own `experiment.json` deck, same netlist): Iq 13.871 uA /
  27.61 uA (transient) vs 13.871 uA / 27.604 uA (op method) at tt/27C/3.30V -- agree (run
  `iqxcheck2_*`). `iqxcheck_*` is the first attempt: the ngspice results are identical but the driver's own
  validity key names were wrong (reported `valid=False`); it is kept (append-only) and superseded by `iqxcheck2_*`.
- Validity rules (`classify()` in the driver; unit-tested in `sim/tests/test_mitigation_probe.py`): a point is
  INVALID, never PASS, if the operating point is non-regulating (VOUT outside 1.7-1.9 V), the unity-gain
  crossing, the phase at crossing or the -180 deg crossing (GM) is missing, or the run raised an ngspice
  solver diagnostic (`singular matrix`, `gmin stepping failed`, `out of range for ^`).
- Provenance in every `result.json`: source commit, SHA-256 of driver / experiment.json / testbench / DUT /
  raw and edited netlist / deck / spiceinit, PDK pin match, ngspice 42 and xschem 3.4.4 (both match the
  `sim/pdk.json` tool pins), ngspice exit code and elapsed time. Complete stimulus = `runs/*/deck.spice`;
  solver output = `runs/*/ngspice.log`.
- Disclosure: the driver was edited twice before the runs that are kept (a `dcg` print added to every
  point; the iq-bench key names fixed). The first three baseline runs were discarded UNCOMMITTED and re-run
  after the `dcg` change (their PM/GM were identical). `driver_sha256` differs between `base_tt_*` (and the
  other early loop-gain runs) and the `repro_*` runs solely because of the later iq-bench-only fix; the
  loop-gain code path is unchanged and `repro_*` reproduce `base_tt` / `rcz0p5_tt` bit-for-bit on every
  PM, GM, crossover, VOUT and Iq value with identical deck and netlist hashes.
- Lint-only edit (review fix, PR #344): `_kind` rename at line 100 to satisfy ruff F841 changes the driver SHA-256 to `71d58d8aa70e65bb63c0d556cf6a77314104aab54b8f5d652dfb9dc9410498b2`; the loop-gain code path is unchanged and no run was repeated, so all recorded `result.json` driver hashes (earlier driver) are left as-is.

## 5. Recommendation: what the evidence supports and refutes

- **Refuted (within the sampled conditions): a fixed internal bleed within the Iq budget as the 0 mA fix.**
  1 uA is the only bleed that fits the tt/50 mA headroom (2.4 uA) and it lowers both 0 mA margins; 3 and 10 uA
  are over budget (and also do not help); at ff/125C there is no 50 mA headroom at all.
- **Partially supported, not within budget: a load-dependent low-frequency pole/doublet at 0 mA.**
  Raising the minimum current moves the 0.33 uF / 0 mA crossover up (283 Hz -> 4.5 kHz at 100 uA) and recovers
  PM only at that cost (62.5 deg at ~100 uA, ~7x the 0 mA Iq), while the 4.7 uF / 0 mA point does not recover
  (22 deg) and dips non-monotonically with bleed (53 -> 34 -> 25 -> 18 -> 22). The PM dip is non-monotonic in
  both bleed and C_COMP, consistent with the crossover landing inside a pole-zero doublet; it is not shown
  here to be a single load-dependent pole (no pole/zero extraction was run).
- **Supported: the 50 mA / 0.33 uF failure is governed by the R_CZ zero/Miller network** (PM follows R_CZ,
  is insensitive to C_COMP and to bleed), and a passive change fixes it at zero Iq cost at all three
  sampled conditions. It is NOT the same mechanism as the 0 mA failure.
- **No screened candidate meets both targets at the sampled conditions.** The 0 mA failures (and, for V1/V2,
  a 4.7 uF / 1 mA regression) remain. "Meets both targets" is also false for the unmodified ff/125C 50 mA Iq.
- **Load-adaptive compensation hypothesis (for a later design issue; not built here).** The data say the
  best R_CZ differs by load: ~0.5x at heavy load (>= ~10 mA) for the 0.33 uF point, ~1x-2x at <= 1 mA for
  4.7 uF. Hypothesis: make R_CZ load-adaptive by splitting it, R_CZ = R_a + (R_b || triode PMOS switch) with
  R_a ~ 0.5x and R_b ~ 0.5x of today's 300 k (so R_CZ_eff between 150 k and 300 k), the switch gate driven
  from the existing sense-mirror current (assumed to scale with load; not verified here, so any light-load Iq adder must be measured)
  with a threshold bounded to 1-10 mA of load. Bounded parameters to explore: R_a/R_b split 0.4-0.6x, threshold
  1-10 mA, switch Iq adder <= 0.5 uA at 0 mA. This addresses 50 mA and 1 mA only; the 0 mA doublet needs a
  separate light-load lever (suggested first look: a two-parameter C_COMP x R_CZ scan below 1 mA, and the
  error-amp tail current, neither screened here). Not developed further, per the issue.
